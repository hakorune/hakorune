# 296x-551A FastMemory Large-File Split Cleanup

## Purpose

Split the large FastMemory/MIR support files before opening more branch-CFG
producer behavior. This is a BoxShape cleanup: it must not add a new accepted
FastMemory route, allocator behavior, benchmark claim, or activation surface.

## Current Inventory

```text
src/mir/fastmem_access_plan.rs                 3038 lines
src/runner/mir_json_emit/metadata.rs           1680 lines
src/mir/function/types.rs                      1506 lines
src/mir/builder/fastmem.rs                     1390 lines
src/mir/direct_array_access_plan.rs            1363 lines
src/cli/provider_package_hako_derived_build.rs 1241 lines
src/stage1/program_json_v0/lowering.rs         1012 lines
```

## Split Order

1. Move inline test modules out of production logic files.
   - `fastmem_access_plan.rs` first because it is the largest file and has the
     next cleanup target.
   - Then `builder/fastmem.rs`, `direct_array_access_plan.rs`, and
     `stage1/program_json_v0/lowering.rs`.

2. Extract FastMemory linked-list plan common cores.
   - Introduce `ResolvedHeadAccess`.
   - Introduce `ResolvedBlockNextAccess`.
   - Introduce a shared list-plan core for `LocalFree`, `FreeHead`, and
     `AtomicRemoteHead` without changing existing report keys.

3. Split catalog-like data definitions only after the FastMemory code is
   smaller.
   - `function/types.rs` should move by metadata family, not by arbitrary line
     count.

4. Split MIR JSON metadata emission by metadata family.
   - Keep data shape unchanged.
   - Move serializer helpers behind profile/family modules.

5. Move provider-package C templates out of Rust source.
   - Keep generated bytes identical before changing template behavior.

## Non-goals

```text
opening MIM-PORT-FMEM-053 branch CFG behavior
renaming public report keys
changing FastMemory access-plan semantics
changing JSON output shape
changing provider package generated C
allocator activation / hook / global allocator claim
```
